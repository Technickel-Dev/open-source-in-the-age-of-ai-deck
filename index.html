> What is Open Source?

Start with the basics

The basics

What is Open Source?

Software whose source code is public, shared under a license that lets anyone use it.

Read it

The code is public

Anyone can see how it works, learn from it and check what it does.

Change it

Anyone can improve it

Fix a bug, add a feature or improve the docs, then send it back to the project.

Share it

The license says you can

Use it, fork it and build on it, within the terms of its license.

Open Source in the age of AI · Technickel
Keep this short. Open Source means the source code is available under a license that allows use, study, modification and sharing. Examples people know: Linux, Python, React, VS Code. The license matters, so check it before reusing anything.

Open Source in the age of AI · Technickel
Quick tour, not legal advice. The bar runs from permissive licenses (MIT, BSD, Apache 2.0), which let you do almost anything with a notice, to copyleft licenses (LGPL, GPL, AGPL), which require derived work you distribute to stay open under the same terms. The grid shows what each lets you do: all four allow commercial use and changes; MIT and Apache let you ship changes closed; GPL and AGPL do not; only the AGPL also counts offering it as a network service as distribution. Apache 2.0 also grants patent rights. The red end of the bar is the copyleft licenses; past it, the dark end holds source-available licenses (BSL, SSPL, Elastic), where you can read the code but the license restricts what you do with it, so they are not open source by the usual definition. Code with no license is not open source either: the author keeps all rights. For anything at work, check with Legal.

Making a change

Six steps to your first PR

  1. 01Find an issue + communicateRead the rules. CONTRIBUTING.md, and the project's AI policy if it has one.
    Talk first. Comment on the issue before you open a PR.
  2. 02Fork the repoYour own copy to experiment in.
  3. 03Clone it with Gitgit clone https://github.com/<you>/<repo>.git
  4. 04Make the changesTest it. Run the project's tests and try your change.
    Keep it focused. Split unrelated changes into separate PRs, or stack them if one builds on another.
  5. 05Stage, commit + pushGit basics in 10 minutes (freeCodeCamp)
  6. 06Open the pull request!Say what changed. Link the issue it closes.
    Quality over quantity. One thoughtful PR beats ten drive-bys. Disclose AI help when asked.

Contributing in the age of AI

Own your AI output

If you don't know what it's doing, don't contribute it. Don't be a MEAT proxy. 🥩

It looks bad on you

A PR you can't explain costs you trust.

It makes the maintainer's life harder

They review, debug and fix what you couldn't.

Prompts that help you understand

  • >"Walk me through this diff line by line, like I'm new to this codebase."
  • >"What could this change break? List the edge cases and risks."
  • >"What would a maintainer push back on, given CONTRIBUTING.md and the code style?"
  • >"Explain how X works and why you did it that way instead of the alternatives."
Open Source in the age of AI · Technickel
If you can't explain what the AI wrote, don't send it, and don't be a meat proxy: a human who just passes the AI's output along without understanding it. It looks bad on you and it makes the maintainer's life harder. Use AI to interrogate its own output: ask it to explain the diff, list what could break, predict maintainer pushback and explain the parts you'd have to defend.

Same workflow, different fit

The takeaway

New AI concepts appear every day, and most were designed and configured for the way their creator works. They slot right into your own project, but a lot of open source projects have nothing like them set up. Bring the idea, then adapt it to how that project already works.

Open Source in the age of AI · Technickel
The AI industry has a name for every piece of the AI development lifecycle: agents, loops, software factories, spec-driven development, skills, MCP, context engineering, subagents, harnesses, evals. Most were made for someone's own workflow. In your own project you can adopt them as they are. In a team you adapt to shared conventions. In someone else's open source project you are at the ground floor of their process, so you shoehorn your workflow into how they do things: their CONTRIBUTING.md, their review habits, their AI policy. Think of a toddler's shape sorter, and the square hole meme: in your own project every shape drops into its own hole, in a team one needs a nudge, and in someone else's project everything goes through the one hole their process allows. Take the idea, not the whole machine.
